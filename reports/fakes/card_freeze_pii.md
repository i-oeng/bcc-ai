## 2. Итог

**Разработка.** Разработку начинать нельзя из-за наличия четырёх критических дефектов (Н-03, Н-05, Н-07, Н-16). Противоречия в правилах обработки операций по замороженной карте, ошибки в проектировании REST API и ссылки на несуществующие требования делают реализацию невозможной.

**Тестирование.** Полное проектирование тестов невозможно, так как для ряда требований отсутствуют ожидаемые результаты, а часть критериев приёмки прямо противоречит функциональным требованиям (Н-03, Н-05, Н-15).

**Что исправить в первую очередь**

1. **Устранение противоречия по операциям.** Исправить требование Ф-2, указав исключения для регулярных платежей согласно Ф-3. (Н-03)
2. **Устранение противоречия по лимиту заморозок.** Исправить ожидаемый результат в строке 55 на ошибку 409 при шестой заморозке. (Н-05)
3. **Устранение риска недоступности процессинга.** Заменить требование об отображении успешной заморозки при недоступности процессинга на синхронный отказ. (Н-07)
4. **Добавление пропущенного требования Ф-6.** Добавить пункт Ф-6 с описанием отправки пуш-уведомления при успешной заморозке. (Н-16)
5. **Исправление методов REST API.** Заменить метод DELETE на POST/PATCH и разнести эндпоинты заморозки и разморозки. (Н-09, Н-10)
6. **Дополнение критериев приёмки для подписок.** Добавить критерии приёмки для проверки успешного прохождения регулярных платежей. (Н-08, Н-15)

Документ содержит критические логические противоречия, архитектурные дефекты REST API и пропуски в требованиях. Без устранения данных замечаний реализация бизнес-логики и интеграции приведет к финансовым и операционным рискам.

**Критичные дефекты**

*Противоречивые*

* **Н-03** (Ф-2, Ф-3, Критерий приёмки 3, строки 34, 35, 54). Требование Ф-2 прямо противоречит требованию Ф-3: первое указывает, что замороженная карта отклоняет все операции, а второе допускает проведение регулярных платежей и подписок.
* **Н-05** (Ф-5, Критерий приёмки 4, B. Статус 409, строки 37, 55). Требование устанавливает лимит в 5 раз в месяц, однако критерий приемки на строке 55 описывает шестую заморозку как успешную, что противоречит лимиту и коду ответа 409 в API.

*Неполные*

* **Н-16** (Ф-5, строка 37). Требование ссылается на несуществующее требование Ф-6, из-за чего невозможно понять, какой канал и текст уведомления должны использоваться.

*Прочие*

* **Н-07** (Требования к интеграции, строка 46). Формулировка допускает опасное финансовое поведение: при недоступности процессинга клиент видит карту замороженной, но фактическая блокировка на стороне процессинга не прошла, что создает риск проведения мошеннических операций по карте.

## 4. Вопросы к заказчику

Блокирующие вопросы нужно закрыть до начала разработки. Чтобы агент учёл ответы, запустите проверку с ключом `--questions-file`, впишите ответы в созданную форму и повторите проверку с ключом `--answers`.

**Блокирующие**

1. **В-1.** Требование Ф-2 запрещает все операции по замороженной карте, а Ф-3 разрешает регулярные платежи и подписки. Разрешено ли списание регулярных платежей и подписок по замороженной карте? Почему важно: Без уточнения правил обработки подписок невозможно реализовать логику процессинга и настроить критерии приёмки. Варианты: (1) Да, регулярные платежи и подписки должны продолжать проводиться; (2) Нет, заморозка блокирует абсолютно все операции без исключений. *(кому: Бизнес-заказчик; нарушения: Н-03; основание: «Замороженная карта отклоняет все операции», строка 34)*
2. **В-2.** В документе отсутствует требование Ф-6 и есть противоречие по шестой заморозке между лимитом и критерием приемки. Какой ожидаемый результат должен быть при попытке шестой заморозки за месяц? Почему важно: Невозможно реализовать валидацию лимитов и написать автотесты без утверждённого поведения системы при исчерпании лимита. Варианты: (1) Операция отклоняется с ошибкой 409; (2) Операция разрешается, лимит носит информационный характер. *(кому: Бизнес-заказчик; нарушения: Н-05, Н-16; основание: «Заморозить карту можно не больше 5 раз в месяц. Уведомление о заморозке отправляется согласно Ф-6», строка 37)*
3. **В-3.** Допускает ли архитектура ложное подтверждение заморозки клиенту при недоступности процессинга или требуется синхронный отказ? Почему важно: Ложное подтверждение заморозки при недоступности процессинга создает критический риск мошенничества и проведения неавторизованных операций. Варианты: (1) Требуется синхронный отказ клиенту с ошибкой при недоступности процессинга; (2) Разрешено асинхронное проведение с локальным изменением статуса. *(кому: Архитектор; нарушения: Н-07; основание: «Если процессинг недоступен, заморозка отображается клиенту как выполненная», строка 46)*
4. **В-4.** Заморозка и разморозка используют один URL /cards/{cardId}/freeze и метод DELETE для заморозки. Как следует перепроектировать эндпоинты API? Почему важно: Использование метода DELETE для изменения статуса нарушает стандарты REST API, а одинаковые пути для разных действий вызывают маршрутные конфликты. Варианты: (1) Разделить на POST /cards/{cardId}/freeze и POST /cards/{cardId}/unfreeze; (2) Использовать единый эндпоинт PATCH /cards/{cardId} с телом статуса. *(кому: Разработка процессинга; нарушения: Н-09, Н-10; основание: «Заморозка карты методом DELETE, разморозка методом POST», строка 91)*

**Важные**

5. **В-5.** Критерий приёмки на строке 54 ожидает отклонение подписки на сумму 2 990 тенге при замороженной карте, что противоречит Ф-3. Какие правила применяются к валюте, счёту и недостатку средств? Почему важно: Отсутствие параметров списания и обработки нехватки средств приводит к дефектам интеграции. Варианты: (1) Валюта тенге, списание со счёта карты, при нехватке средств отказ по коду недостаточности; (2) Валюта тенге, списание с привязанного счета. *(кому: Разработка процессинга; нарушения: Н-08; основание: «Карта заморожена / Списание подписки 2 990 ₸ / Операция отклонена», строка 54)*
6. **В-6.** Требование Ф-3 не имеет подтверждающего критерия приемки. Требуется ли добавить отдельный позитивный тест-кейс для успешного списания подписки? Почему важно: Без критерия приемки невозможно проверить реализацию требования Ф-3 при тестировании. Варианты: (1) Да, добавить критерий успешного списания подписки по замороженной карте; (2) Нет, достаточно существующих проверок. *(кому: Бизнес-заказчик; нарушения: Н-15; основание: «Регулярные платежи и подписки по замороженной карте продолжают проводиться», строка 35)*
