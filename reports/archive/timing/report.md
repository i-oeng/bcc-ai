**Главные дефекты:**

1. [Н-07](#н-07) (Требования к интеграции, B. Общие параметры, B. Общие параметры, B. Общие параметры): Метод GET используется для сохранения настроек (сохранение порога), а в CURL передаются параметры изменения состояния.
1. [Н-09](#н-09) (B. Пример 200 ERROR): Метод возвращает HTTP 200 OK при наличии бизнес-ошибки, что противоречит общепринятой семантике REST API и кодам ошибок в документе (например, ТР-44), где ошибки возвращаются с соответствующими статус-кодами (400).
1. [Н-11](#н-11) (Требования к данным): В одной строке денежные величины хранятся в разных единицах (тиыны и тенге): при сравнении суммы с порогом возможна ошибка в 100 раз.
1. [Н-17](#н-17) (документ): В разделе нефункциональных требований указано только время передачи push, но полностью отсутствуют требования к доступности (availability), безопасности (security), журналированию (logging) и хранению персональных данны…

**Спросить у заказчика в первую очередь:**

* [В-1](#в-1) В спецификации для сохранения порога используется HTTP-метод GET, что нарушает стандарты REST API и приводит к передаче параметров состояния через query. Какой HTTP-метод следует использовать для сох…
* [В-2](#в-2) В требованиях к хранению суммы указаны в тиынах, а порог: в тенге. В какой единице измерения необходимо хранить и сравнивать порог и суммы?
* [В-3](#в-3) Метод возвращает бизнес-ошибку со статус-кодом HTTP 200 OK. Каким должен быть HTTP-статус для ответа с ошибкой валидации?
* [В-4](#в-4) Для чужой карты спецификация требует возвращать 404 вместо 403, что противоречит описанию статус-кода 403. Какой код нужно возвращать для чужой карты?

### Блокирующие

<a id="в-1"></a>**В-1. В спецификации для сохранения порога используется HTTP-метод GET, что нарушает стандарты REST API и приводит к передаче параметров состояния через query. Какой HTTP-метод следует использовать для сохранения настроек?**

* **Кому:** Архитектор
* **Контекст:** «REST type\|GET» (с. 3, строка 114, раздел «Часть B. REST API > Общие параметры»)
* **Почему важно:** Без изменения метода на POST или PUT разработка не сможет корректно реализовать обработку тела запроса и идемпотентность на уровне API.
* **Варианты ответа:** (1) Использовать POST с передачей данных в теле запроса (JSON); (2) Использовать PUT с передачей данных в теле запроса (JSON); (3) Оставить GET, перенеся параметры в path
* **Связанные находки:** [Н-07](#н-07)

<a id="в-2"></a>**В-2. В требованиях к хранению суммы указаны в тиынах, а порог: в тенге. В какой единице измерения необходимо хранить и сравнивать порог и суммы?**

* **Кому:** Разработка процессинга
* **Контекст:** «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге» (с. 2, строка 56, раздел «Часть A. Новый функционал > Требования к данным»)
* **Почему важно:** Разные единицы измерения приведут к ошибкам сравнения в 100 раз и ложным срабатываниям уведомлений.
* **Варианты ответа:** (1) Хранить все денежные величины в тиынах (целые числа); (2) Хранить все денежные величины в тенге с поддержкой копеек/тиынов (дробные); (3) Оставить как есть, выполняй конвертацию на лету
* **Связанные находки:** [Н-11](#н-11)

<a id="в-3"></a>**В-3. Метод возвращает бизнес-ошибку со статус-кодом HTTP 200 OK. Каким должен быть HTTP-статус для ответа с ошибкой валидации?**

* **Кому:** Архитектор

1. **Исправление HTTP-метода для сохранения.** Изменить метод REST API с GET на POST или PUT и скорректировать параметры запроса. ([Н-07](#н-07))
2. **Устранение разногласий в единицах измерения.** Привести все денежные суммы в требованиях к данным и логике к единой минимальной валютной единице (тиыны). ([Н-11](#н-11))

4. **Согласование типов данных в API.** Привести параметр amount в запросе и ответе к единому типу данных (integer или string). ([Н-13](#н-13))
5. **Дополнение нефункциональных требований.** Добавить требования к доступности, логированию и информационной безопасности. ([Н-17](#н-17))
6. **Заполнение метаданных и чек-листа документа.** Указать версию, дату, заполнить таблицу чек-листа ревью и блок согласующих лиц. ([Н-18](#н-18), [Н-19](#н-19), [Н-20](#н-20), [Н-21](#н-21))

## Приложение A. Как работает проверка

1. Документ прочитан и приведён к тексту с номерами строк; чувствительные данные (карты, ИИН, IBAN, телефоны, e-mail, токены, ФИО) заменены плейсхолдерами до отправки в модель, исходные значения возвращены только в этом отчёте.

3. Детерминированные правила проверили размытые слова, пустые поля шаблона, версию, приоритеты, единицы, семантику HTTP и коды ответа.

6. По подтверждённым находкам модель составила вопросы для уточнения и итог; решение о готовности принимает код.
