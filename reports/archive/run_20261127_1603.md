Отчёт сформирован агентом автоматически. Каждое нарушение ссылается на строку проверяемого документа.

## Кратко

* **Разработка:** НЕЛЬЗЯ начинать (критичных дефектов: 6).
* **Тестирование:** НЕЛЬЗЯ проектировать тесты полностью (критичных дефектов, при которых ожидаемый результат не определён: 5).
* **Требований:** 42; **открытых нарушений:** 41 (критичных 6, существенных 25, незначительных 10); **вопросов заказчику:** 9, из них блокирующих 5.

**Главные дефекты:**

1. [Н-03](#н-03) (Ф-1, B. Логика п. 4). Требование Ф-1 описывает изменение/сохранение настроек порога, но в связанной дочерней спецификации REST API (Часть B, строки 114-119) для метода сохранения назначен тип HTTP GET, а параметры передаются в Query/CURL, что нарушает стандарты REST (неидемпотентное/изменяющее состояние действие должно быть POST/PUT) и создает риск безопаснос…
   «Ф-1. Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно» (с. 1, строка 39, раздел «Часть A. Новый функционал > Функциональные требования») / «REST type\|GET» (с. 3, строка 114, раздел «Часть B. REST API > Общие параметры»)
   [В-3](#в-3) Какая сигнатура и контракт ошибки должны быть у метода сохранения порога /alerts/saveLimit?
1. [Н-05](#н-05) (Ф-2, Критерий приёмки 2). Противоречие между требованием Ф-2 и Критерием приёмки 2. По Ф-2 месяц определяется по дате совершения покупки (31 января, январский счётчик). В критерии приёмки указано, что вырос февральский счётчик.
   «Месяц определяется по дате совершения покупки в Алматы» (с. 1, строка 41, раздел «Часть A. Новый функционал > Функциональные требования») / «Покупка 31 января в 23:58 на 4 000 ₸\|Провести 1 февраля в 00:03 по Алматы\|Февральский счётчик вырос на 4 000 ₸» (с. 2, строка 73, раздел «Часть A. Новый функционал > Критерии приемки»)
   [В-2](#в-2) По какой дате следует определять календарный месяц для накопления расходов: по дате совершения покупки (как в Ф-2) или по дате проведения (клиринга, как в Критерии приёмки 2)?
1. [Н-17](#н-17) (B. Логика п. 5, B. Статус 400, B. Пример 200 ERROR). Возврат ошибки бизнеса/валидации ("result":"ERROR") с HTTP-статусом 200 OK противоречит спецификации REST API и описанию статуса 400 (строка 184). Ошибки валидации входных параметров должны возвращаться со статусом 400 Bad Request.
   «5. При отклонении суммы вернуть прежнее состояние и результат ERROR» (с. 3, строка 136, раздел «Часть B. REST API > Логика работы метода») / «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный» (с. 4, строка 171, раздел «Часть B. REST API > Ответ»)
   [В-3](#в-3) Какая сигнатура и контракт ошибки должны быть у метода сохранения порога /alerts/saveLimit?
1. [Н-25](#н-25) (B. Пример 400). Противоречие в формате ответа при ошибке 400. В примере под разделом 200 (строка 192) бизнес-ошибка возвращается в теле со статусом 200 и полями result и message, а в ТР-38 (строка 198) при коде 400 возвращается тело без поля result. Это сбивает клиентов API и блокирует разработку единого парсера ответов.
   «{"message":"Некорректный запрос"}» (с. 4, строка 198, раздел «Часть B. REST API > 400. Unsuccessful — Bad request») / «{"result":"ERROR","message":"Проверьте сумму"}» (с. 4, строка 192, раздел «Часть B. REST API > или»)
   [В-3](#в-3) Какая сигнатура и контракт ошибки должны быть у метода сохранения порога /alerts/saveLimit?
1. [Н-26](#н-26) (A. UI дизайн, A. Интеграция 1). Отсутствие описания метода чтение настроек: экран UI (ТР-03) и требования к интеграции (ТР-12) требуют чтения текущих настроек, но спецификация API содержит только метод сохранения GET /alerts/saveLimit. Эндпоинт для получения настроек отсутствует.
   «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»» (с. 2, строка 60, раздел «Часть A. Новый функционал > Требования к интеграции») / «Функциональные требования: чтение порога» (с. 3, строка 113, раздел «Часть B. REST API > Общие параметры»)
   [В-4](#в-4) Отсутствует спецификация API для чтения текущих настроек лимита карты. Каков контракт данного метода?
1. [Н-30](#н-30) (Ф-2, A. Данные). Противоречие в расчёте расходов и составе данных: Ф-2 требует уменьшать расходы месяца *исходной покупки* при возврате, однако раздел «Требования к данным» не содержит поля для связывания возврата с исходной операцией (нет original_operation_id / parent_id), храня лишь идентификатор самой операции и её месяц.
   «Возврат уменьшает расходы месяца исходной покупки» (с. 1, строка 41, раздел «Часть A. Новый функционал > Функциональные требования») / «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге» (с. 2, строка 56, раздел «Часть A. Новый функционал > Требования к данным»)

<a id="в-1"></a>**В-1. По какой дате определять месяц расходов: по дате совершения покупки или по дате её проведения?**

* **Кому:** Бизнес-заказчик
* **Контекст:** «Покупка 31 января в 23:58 на 4 000 ₸\|Провести 1 февраля в 00:03 по Алматы\|Февральский счётчик вырос на 4 000 ₸» (с. 2, строка 73, раздел «Часть A. Новый функционал > Критерии приемки»)
* **Почему важно:** По Ф-2 покупка от 31 января относится к месяцу совершения. Критерий приёмки учитывает её в месяце проведения (1 февраля): Февральский счётчик вырос на 4 000 ₸.
