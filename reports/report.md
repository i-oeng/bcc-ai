## Итог

**Разработка.** Разработку начинать НЕЛЬЗЯ из-за 7 критичных дефектов, которые делают невозможной корректную реализацию. В частности, отсутствует эндпоинт чтения настроек (Н-22), метод сохранения нарушает REST-семантику (Н-34), а логика определения месяца покупки и хранения времени операции противоречит критериям приёмки (Н-07, Н-37).

**Тестирование.** Тестирование НЕЛЬЗЯ проектировать полностью, так как для 6 критичных дефектов не определён ожидаемый результат. Невозможно однозначно задать проверки для группировки расходов по месяцам (Н-07), кодов ответа API при ошибках валидации и доступе к чужой карте (Н-29, Н-28), а также для нагрузочного тестирования НФТ (Н-16).

### Что исправить в первую очередь

1. **Устранить противоречие в определении месяца покупки и хранении времени операции.** Согласовать Ф-2 и критерий приёмки 2, добавить хранение точной даты/времени операции с часовым поясом и перевести все суммы в тиыны. ([Н-07](#н-07), [Н-37](#н-37), [Н-40](#н-40))
2. **Исправить контракт REST API для чтения и сохранения настроек.** Добавить метод GET /alerts/getLimit для чтения настроек, перевести /alerts/saveLimit на POST с JSON-телом и убрать лишний Content-Type у GET. ([Н-22](#н-22), [Н-34](#н-34), [Н-32](#н-32))
3. **Согласовать коды ответов API при ошибках валидации и доступе к чужой карте.** Определить единый HTTP-код для ошибки валидации суммы (400 или 200), уточнить возврат 403/404 для чужой карты и привести перечень статусов в соответствие с примерами. ([Н-29](#н-29), [Н-28](#н-28), [Н-42](#н-42), [Н-43](#н-43), [Н-44](#н-44))
4. **Сделать проверяемыми нефункциональные требования.** Указать перцентиль, целевую нагрузку (RPS), точки отсчёта времени, требования к доступности и скорректировать формулировку бизнес-цели. ([Н-16](#н-16), [Н-39](#н-39), [Н-01](#н-01))
5. **Уточнить граничные сценарии и модель данных.** Описать поведение при снижении порога ниже текущих расходов, возврате за прошлый месяц, ключ идемпотентности и согласовать таблицы БД. ([Н-12](#н-12), [Н-08](#н-08), [Н-19](#н-19), [Н-24](#н-24))

Документ имеет базовую структуру, но не готов к передаче в разработку и тестирование. В тексте присутствуют 7 критичных и 24 существенных дефекта, включая прямые противоречия между бизнес-логикой, критериями приёмки и спецификацией REST API. Требуется доработка и согласование документа со смежными командами до старта реализации.

<a id="в-1"></a>**В-1.** В Ф-2 (строка 41) месяц определяется по дате совершения покупки, а в критерии приёмки 2 (строка 73) покупка от 31 января, проведённая 1 февраля, увеличивает февральский счётчик. Какое правило верно? *(Бизнес-заказчик / [Н-07](#н-07))*

<a id="в-2"></a>**В-2.** Бизнес-цель (строка 21) указывает информирование «в момент покупки», Ф-2 (строка 41) учитывает только проведённые покупки (клиринг), а НФТ (строка 52) допускает задержку до 1 минуты. Какой момент отправки push считать целевым? *(Бизнес-заказчик / [Н-01](#н-01), [Н-02](#н-02))*  
Варианты: (1) При проведении покупки (клиринге) с задержкой отправки push до 1 минуты; (2) В момент авторизации на терминале с задержкой отправки push до 1 минуты.

<a id="в-3"></a>**В-3.** ТР-12 (строка 60) и Description (строка 113) требуют чтение порога через REST API, но в части B описан только метод сохранения /alerts/saveLimit. Какой эндпоинт должен использоваться для чтения настроек? *(Аналитик / [Н-22](#н-22))*

<a id="в-4"></a>**В-4.** Для изменения состояния (сохранения порога) в строке 114 указан метод GET и одновременно заголовок Content-Type: application/json (строка 165). Переводим ли метод на POST с передачей параметров в теле запроса? *(Архитектор / [Н-34](#н-34), [Н-32](#н-32))*  
Варианты: (1) Изменить метод на POST и передавать параметры в JSON-теле запроса; (2) Оставить GET, но удалить заголовок Content-Type: application/json.

<a id="в-5"></a>**В-5.** При ошибке валидации суммы шаг 5 (строка 136) и пример ответа (строка 192) возвращают HTTP 200 с result: ERROR, а описание статуса 400 (строка 184) говорит о неверных параметрах запроса. Какой HTTP-код возвращать при невалидной сумме? *(Аналитик / [Н-29](#н-29))*  
Варианты: (1) Возвращать HTTP 400 Bad Request с телом ошибки; (2) Возвращать HTTP 200 с result: ERROR, а HTTP 400 использовать только для отсутствующих обязательных параметров.

<a id="в-6"></a>**В-6.** В перечне статусов (строка 194) указан код 403 для запрещённого доступа, но в строке 206 написано возвращать 404 для чужой карты (при этом 404 нет в общем списке статусов). <a id="в-7"></a>**В-7.** В НФТ (строка 52) не указаны перцентиль, целевая нагрузка (RPS), точки отсчёта времени и требования к доступности сервиса. Какие значения принять для разработки и нагрузочного тестирования? *(Архитектор / [Н-16](#н-16), [Н-39](#н-39))*

### Нарушения уровня набора

<a id="н-37"></a>**Н-37** / Критично / Непротиворечивость / ТР-06 (Ф-2), ТР-11 (A. Требования к данным)  
Требование Ф-2 обязывает группировать расходы по месяцу совершения покупки в часовом поясе Алматы. При этом структура данных (ТР-11) не хранит дату/время совершения покупки, а хранит только атрибут «месяц» (без указания часового пояса и точного времени совершения). Это делает невозможным перерасчёт или корректную организацию агрегаций при возвратах и разнице во времени.

> «Месяц определяется по дате совершения покупки в Алматы» (с. 1, строка 41)  
> «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге» (с. 2, строка 56)  

**Исправить:** Добавить в требования к данным обязательное хранение точной даты и времени совершения операции с указанием часового пояса (или UTC), либо хранить дату совершения покупки в формате YYYY-MM-DD по времени Алматы.

<a id="н-34"></a>**Н-34** / Критично / Выполнимость набора / ТР-05 (Ф-1), ТР-12 (A. Интеграция REST API), ТР-20 (B. Логика п. 4)  
Использование метода GET для сохранения (изменения) настройки нарушает стандарты REST API, так как GET должен быть безопасным и идемпотентным без изменения состояния на сервере.

> «Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно» (с. 1, строка 39)
